# v0.2 Local Usable MVP Spec

Date: 2026-06-18
Status: Proposed
Mode: Hard cutover, no legacy product path, no fallbacks, no backward compatibility

## Source Context

This spec follows:

- `docs/qgenda-physician-scheduling-research.md`
- `docs/architecture.md`
- `docs/specs/v0.1-generator-spec.md`

v0.1 proves the core scheduling engine:

- typed `ScheduleScenario` input
- deterministic solver invocation
- hard-rule validation
- fairness ledger
- cluster scorecard
- CLI and native JSON fixtures

v0.2 makes the system usable by a physician scheduler without editing scenario JSON.

The product goal is not to add a large enterprise surface. The product goal is to let one real user
maintain the facts of a scheduling period, generate a schedule, review whether it is fair and valid,
and share the resulting calendar.

## Product Thesis

Humans should not edit solver input.

v0.2 introduces a planning layer above the v0.1 engine:

```text
Human planning forms
  -> Planning model
  -> Scenario compiler
  -> Existing generator engine
  -> Schedule review and export
```

The v0.1 scenario JSON becomes a compiled artifact. It remains useful for engine tests and
reproducibility, but it is no longer the human-facing product API.

The highest-layer solution is a small local application with:

- structured roster entry
- structured demand templates
- date exceptions
- vacation/unavailability ranges
- holiday and weekend-block setup
- generation run history
- calendar review
- fairness scorecard
- printable and calendar-share outputs

The LLM belongs later as an extraction assistant. It may eventually read policy notes, emails, or
pasted documents and propose structured facts. It must not be the final assignment authority. v0.2
uses forms only.

## Target User

Primary v0.2 user:

- one scheduling owner or technical operator
- one physician stakeholder reviewing output quality

Secondary reviewer:

- doctors receiving a static calendar, ICS file, or printed schedule

Out of scope:

- general physician self-service
- multi-admin approval workflows
- cloud-hosted departmental deployment

## Final State

v0.2 is complete when a user can:

1. Start a local web app.
2. Enter and edit providers, eligibility, FTE, vacations, holidays, weekend blocks, demand templates,
   and date exceptions through forms.
3. Generate a monthly schedule without hand-writing JSON.
4. Review the generated schedule in a calendar/grid UI.
5. See hard-rule status, infeasibility diagnostics, fairness ledger, and cluster metrics.
6. Export or share the schedule as:
   - printable HTML
   - CSV review file
   - ICS calendar file for all providers
   - ICS calendar file for a single provider
7. Re-run the same planning snapshot and get the same compiled scenario hash and deterministic result.

The current v0.1 engine remains the assignment authority. The new app may compile inputs, call the
engine, store snapshots, and present results. It may not make hidden assignments outside the engine.

## Hard Cutover Position

v0.2 is a product cutover from raw scenario editing to planning-state editing.

Rules:

- One human-facing planning model.
- One compiler from planning model to engine scenario.
- One engine schedule result contract.
- One calendar/date classifier.
- One rule catalog.
- One fairness ledger implementation.
- One scorecard implementation.
- One local persistence store.
- No parallel "manual schedule builder" path.
- No UI rule reimplementation.
- No UI-generated assignments.
- No raw scenario JSON editor in the product UI.
- No compatibility importer for old v0.1 scenario files.
- No fallback greedy scheduler if the solver is unavailable or infeasible.
- No public share links.
- No hidden defaults for business policy that should be explicit.

The v0.1 fixtures can remain as engine fixtures. They must not be treated as the v0.2 product input
model.

## Capability Contract

### The App Can

- Store a local planning workspace.
- Validate planning inputs before generation.
- Compile planning inputs into a complete engine scenario.
- Generate a schedule by calling the existing core generator.
- Persist immutable run snapshots.
- Display schedule results.
- Display fairness and cluster metrics from the engine result.
- Export generated schedules.
- Reproduce a run from stored snapshots.

### The App Cannot

- Infer missing policies.
- Infer provider eligibility from names.
- Import spreadsheets, calendars, QGenda, or EHR data.
- Let the UI bypass validation.
- Let the UI edit compiled engine JSON directly.
- Let the UI create assignments directly.
- Repair schedules by manually moving assignments.
- Publish schedules to a cloud service.
- Protect sensitive hospital data in a production compliance posture.

### The Compiler Can

- Expand date ranges into unavailable dates.
- Expand weekly demand templates into daily demand.
- Apply explicit date exceptions.
- Attach holidays to day demand.
- Attach weekend blocks to day demand.
- Compute opening ledger input.
- Produce a complete `ScheduleScenario` for a horizon.
- Return structured compile diagnostics.

### The Compiler Cannot

- Solve assignments.
- Score fairness.
- Decide unknown dental days.
- Guess whether a holiday is major or minor.
- Guess whether a provider does call.
- Guess room counts for missing templates.
- Convert soft preferences into solver policy unless the engine has an explicit typed field for them.

## SME Product Moves

A scheduling SME would separate five things that are often mixed together:

1. People facts: who exists, FTE, eligibility, active dates.
2. Calendar facts: holidays, long weekends, vacations, closures.
3. Demand facts: how many lists/rooms/clinics are needed on each date.
4. Policy rules: what cannot happen and what should be balanced.
5. Assignment outputs: the generated schedule and its fairness evidence.

v0.2 must preserve those boundaries in the product model.

The scheduler should be able to answer:

- Is this provider eligible for call?
- Is this provider available on this date?
- What is the demand pattern for a normal Wednesday?
- What changed on this specific Wednesday?
- Which dates belong to the Memorial Day weekend block?
- What fairness debt existed before this month?
- What exact facts were compiled into the solver?
- Why was generation invalid or infeasible?
- What was the resulting fairness spread?

The app should not make the user enter every day one at a time. Daily demand is generated from weekly
templates plus exceptions.

## Architecture

### Runtime

Continue using:

- TypeScript
- Bun
- Effect Schema
- MiniZinc behind the existing solver port
- Biome

Add:

- SQLite for local persistence
- Drizzle for typed schema and migrations
- Hono for the local HTTP API
- React and Vite for the web UI
- a deterministic RFC 5545 ICS exporter owned by core; an external ICS library is allowed only if it
  preserves byte-stable run-snapshot output

Rationale:

- The hardest product problem is contract ownership, not framework novelty.
- The app needs durable state once forms exist.
- SQLite is enough for one-user local operation and supports reproducible snapshots.
- Hono is a small adapter layer over typed services.
- React/Vite is sufficient for a focused operational UI.
- The core engine should remain independent of storage, HTTP, and UI.

## Planning Domain Model

The planning model is the human-facing source of truth.

### Planning Workspace

```json
{
  "schema_version": "v0.2",
  "workspace_id": "local",
  "timezone": "America/Los_Angeles",
  "active_cycle_start": "2026-01-01",
  "active_cycle_end": "2026-12-31",
  "opening_ledger_start_fresh": false
}
```

Rules:

- v0.2 supports one local workspace.
- The workspace timezone is explicit.
- The active cycle supports annual fairness carry-forward.
- `opening_ledger_start_fresh` is the explicit confirmation that missing opening-ledger rows should
  default to zero for the current cycle.
- No multi-workspace UI is required.

### Provider

```json
{
  "provider_id": "dr_smith",
  "display_name": "Dr. Smith",
  "fte": 1.0,
  "call_eligible": true,
  "eye_eligible": false,
  "dental_eligible": true,
  "active_from": "2026-01-01",
  "active_until": null
}
```

Rules:

- `provider_id` is stable and never derived from display name after creation.
- `display_name` is presentation only.
- `fte` is greater than 0 and less than or equal to 1.
- Non-call providers compile to `call_eligible: false`.
- Part-time status is modeled by `fte`; part-time does not automatically imply non-call unless the
  user sets `call_eligible: false`.

### Provider Unavailability

```json
{
  "unavailability_id": "vacation_smith_2026_01_12",
  "provider_id": "dr_smith",
  "start_date": "2026-01-12",
  "end_date": "2026-01-16",
  "kind": "vacation",
  "label": "Vacation"
}
```

Rules:

- Date ranges are inclusive.
- Ranges compile to the engine's `unavailable_dates`.
- `kind` is one of `vacation`, `conference`, `leave`, `other`.
- v0.2 treats all kinds as hard unavailable dates.
- Soft preferences are not part of v0.2.

### Demand Template

```json
{
  "template_id": "weekday_standard",
  "weekday": "wednesday",
  "room_count": 6,
  "normal_list_slots": 5,
  "eye_slots": 1,
  "dental_slots": 0,
  "call_required": true,
  "active_from": "2026-01-01",
  "active_until": null
}
```

Rules:

- Demand templates are weekly patterns.
- Multiple active templates for the same weekday and date are invalid.
- A horizon date must compile from exactly one template or one date exception.
- `normal_list_slots + eye_slots + dental_slots <= room_count`.
- Eye/dental slots are demand facts, not provider preferences.

### Date Demand Exception

```json
{
  "exception_id": "dental_2026_01_15",
  "date": "2026-01-15",
  "room_count": 6,
  "normal_list_slots": 4,
  "eye_slots": 0,
  "dental_slots": 2,
  "call_required": true,
  "label": "Dental clinic day"
}
```

Rules:

- A date exception is a full-day replacement, not a partial patch.
- The UI may prefill it from the compiled template value, but persisted exception values are complete.
- If a day is closed, store a complete exception with zero slots and `call_required: false`.
- This avoids ambiguous merge semantics.

### Holiday

```json
{
  "holiday_id": "memorial_day_2026",
  "date": "2026-05-25",
  "label": "Memorial Day",
  "class": "major",
  "weekend_block_id": "memorial_day_weekend_2026"
}
```

Rules:

- Holidays are explicit.
- Class is `major` or `minor`.
- Holiday class controls burden weight only.
- Holidays do not automatically close a day; demand still comes from template or exception.

### Weekend Block

```json
{
  "weekend_block_id": "memorial_day_weekend_2026",
  "label": "Memorial Day weekend",
  "dates": ["2026-05-22", "2026-05-23", "2026-05-24", "2026-05-25"],
  "split_required": true,
  "required_distinct_call_providers": 2
}
```

Rules:

- Friday night is represented by including the Friday date.
- Long weekends are represented by explicit date arrays.
- If `split_required` is true, the engine enforces distinct call providers.
- Weekend block membership is compiled into day demand.

### Opening Ledger

```json
{
  "provider_id": "dr_smith",
  "cycle_start": "2026-01-01",
  "as_of_date": "2026-02-01",
  "call_burden": 3.0,
  "weekend_burden": 1.5,
  "holiday_burden": 0.0,
  "first_count": 3,
  "second_count": 2,
  "middle_count": 7,
  "last_count": 1,
  "eye_count": 0,
  "dental_count": 1
}
```

Rules:

- Opening ledger is entered or adjusted by the scheduler.
- It is not imported from historical systems in v0.2.
- The compiler selects rows matching the generation cycle and horizon.
- Missing provider ledger rows default to zero only after the user confirms "start fresh" for the
  cycle.

### Generation Request

```json
{
  "horizon": {
    "start_date": "2026-03-01",
    "end_date": "2026-03-31"
  },
  "solver": {
    "max_seconds": 30,
    "random_seed": 1,
    "allow_feasible_result": false
  }
}
```

Rules:

- The horizon must be contiguous.
- The horizon must be fully covered by demand templates or exceptions.
- The solver settings are visible but defaulted.
- `allow_feasible_result` remains false by default.

## Scenario Compiler

### Public Function

```ts
type CompilePlanningScenarioInput = {
  workspace: PlanningWorkspace
  providers: ProviderPlan[]
  unavailability: ProviderUnavailability[]
  demandTemplates: DemandTemplate[]
  dateExceptions: DateDemandException[]
  holidays: HolidayPlan[]
  weekendBlocks: WeekendBlockPlan[]
  openingLedger: OpeningLedgerPlan[]
  generation: GenerationRequest
}

type CompilePlanningScenarioResult =
  | {
      status: "valid"
      scenario: ScheduleScenario
      diagnostics: CompileDiagnostic[]
    }
  | {
      status: "invalid_input"
      diagnostics: CompileDiagnostic[]
    }
```

Contract:

- Pure function.
- No database access.
- No file access.
- No solver calls.
- No network calls.
- Rejects unknown fields at boundary.
- Emits stable diagnostic codes.

### Compiler Steps

1. Decode planning input with Effect Schema.
2. Validate provider IDs and references.
3. Expand horizon dates.
4. Expand demand templates by date.
5. Apply full-day demand exceptions.
6. Validate every horizon date has exactly one demand source.
7. Expand unavailability ranges into provider unavailable dates.
8. Attach holiday IDs to day demand.
9. Attach weekend block IDs to day demand.
10. Select opening ledger rows.
11. Build engine `ScheduleScenario`.
12. Compute scenario hash.
13. Return scenario plus diagnostics.

### Compile Diagnostics

Examples:

- `C_DUPLICATE_PROVIDER_ID`
- `C_UNKNOWN_PROVIDER_REFERENCE`
- `C_PROVIDER_INACTIVE_IN_HORIZON`
- `C_UNAVAILABILITY_OUTSIDE_ACTIVE_DATES`
- `C_MULTIPLE_DEMAND_TEMPLATES_FOR_DATE`
- `C_MISSING_DEMAND_FOR_DATE`
- `C_DATE_EXCEPTION_OUTSIDE_HORIZON`
- `C_DEMAND_EXCEEDS_ROOM_COUNT`
- `C_HOLIDAY_OUTSIDE_HORIZON`
- `C_WEEKEND_BLOCK_DATE_OUTSIDE_HORIZON`
- `C_WEEKEND_BLOCK_UNKNOWN_HOLIDAY`
- `C_OPENING_LEDGER_UNKNOWN_PROVIDER`
- `C_NO_CALL_ELIGIBLE_PROVIDERS`
- `C_NO_EYE_ELIGIBLE_PROVIDERS`
- `C_NO_DENTAL_ELIGIBLE_PROVIDERS`

Diagnostic shape:

```json
{
  "code": "C_MISSING_DEMAND_FOR_DATE",
  "severity": "error",
  "message": "No demand template or exception covers 2026-03-14.",
  "path": ["demand"],
  "date": "2026-03-14"
}
```

The compiler may emit warnings, but generation is blocked when any diagnostic has severity `error`.

```json
{
  "run_id": "run_2026_03_01_120000",

  "horizon_start": "2026-03-01",
```

## HTTP API Design

All routes are local-only v0.2 routes.

Base:

```http
/api/v0_2
```

### Planning Bootstrap

```http
GET /api/v0_2/planning
```

Returns the complete editable planning state for the local workspace.

```http
PUT /api/v0_2/planning
Content-Type: application/json
```

Replaces the complete planning state after schema and planning validation.

Rationale:

- One-user local app.
- Whole-state replacement is simpler and easier to validate.
- Fine-grained patch APIs can wait until collaborative editing exists.

### Compile Preview

```http
POST /api/v0_2/scenarios/compile
Content-Type: application/json
```

Body:

```json
{
  "horizon": {
    "start_date": "2026-03-01",
    "end_date": "2026-03-31"
  }
}
```

Returns:

- `200` with compiled scenario summary when valid
- `400` with compile diagnostics when invalid

The response may include the full compiled scenario behind an explicit development flag. The normal
UI should display summaries and diagnostics, not raw engine JSON.

### Generate Schedule

```http
POST /api/v0_2/schedule-runs
Content-Type: application/json
```

Body:

```json
{
  "horizon": {
    "start_date": "2026-03-01",
    "end_date": "2026-03-31"
  },
  "solver": {
    "max_seconds": 30,
    "random_seed": 1,
    "allow_feasible_result": false
  }
}
```

Response mapping:

- `201` for `optimal`
- `201` for explicitly allowed `feasible`
- `400` for compile or engine `invalid_input`
- `409` for engine `infeasible`
- `500` for `solver_error`

All responses include a `run_id` only when a run snapshot was created. Invalid compile previews do not
create schedule runs.

### Run History

```http
GET /api/v0_2/schedule-runs
GET /api/v0_2/schedule-runs/:run_id
```

Run detail returns:

- result status
- assignments
- hard-rule report
- scorecard
- warnings
- compiled scenario hash
- created timestamp

### Export

```http
GET /api/v0_2/schedule-runs/:run_id/export/print
GET /api/v0_2/schedule-runs/:run_id/export/csv
GET /api/v0_2/schedule-runs/:run_id/export/ics
GET /api/v0_2/schedule-runs/:run_id/export/ics?provider_id=dr_smith
```

Rules:

- Exports consume `ScheduleResult`.
- Exports do not recompute assignments.
- ICS exports contain provider schedule events only.
- No patient data.
- No hidden personal notes unless explicitly marked exportable.

## Error Model

Status families:

- `invalid_planning`: planning state cannot compile
- `invalid_input`: compiled engine scenario failed engine validation
- `infeasible`: solver proved no schedule satisfies hard constraints
- `solver_error`: solver failed unexpectedly
- `optimal`: solver produced and proved optimal result
- `feasible`: allowed only when explicitly enabled

The web API maps these into HTTP status codes, but the product UI should show domain statuses.

Expected failures are data, not thrown strings.

## Acceptance Criteria

### Product

- A user can create a complete month from forms.
- A user does not need to edit JSON.
- A user does not need to enter every day one by one.
- Vacations can be entered as date ranges.
- Dental/eye clinic dates can be represented through templates or full-day exceptions.
- Long weekends can be represented explicitly.
- Opening fairness debt can be entered.
- Generation produces a persisted run.
- The run review shows schedule and scorecard.
- Exports are available from the run review.

### Correctness

- Compiled scenarios are accepted by the existing engine schema.
- Engine hard-rule violations remain zero for feasible schedules.
- Non-call provider constraints remain enforced.
- Post-call day off remains enforced.
- No consecutive calls remain enforced.
- Eye/dental eligibility remains enforced.
- Weekend split remains enforced.
- Fairness ledger comes from core scorecard code.
- UI does not recompute fairness.
- Export output matches stored run assignments.

### Reproducibility

- Every run stores planning snapshot, compiled scenario, scenario hash, result, solver metadata, and
  app version.
- Re-running the stored compiled scenario produces the same deterministic assignment ordering when
  solver settings and backend match.
- Exporting the same run twice produces byte-stable CSV and ICS except for intentionally excluded
  generation timestamps.

### Engineering

- Root `src/` is removed after workspace migration.
- Existing engine modules live under `packages/core`.
- Storage code is isolated under `packages/storage`.
- Hono route handlers are thin adapters.
- React components call typed client APIs.
- No scheduling rules are implemented in route handlers.
- No scheduling rules are implemented in React components.
- No direct MiniZinc references exist outside the solver adapter.
- No duplicate date/weekend classifier exists.
- No duplicate scorecard implementation exists.

## Non-Goals And Rationale

### No Auth

The MVP is local and one-user. Auth adds surface without addressing scheduling correctness.

### No Cloud Sharing

Calendar data includes staff schedules and absence information. Public links are not appropriate
until there is an auth and security posture.

### No Input Importers

Spreadsheet, QGenda, and calendar imports will obscure whether the product model is correct. v0.2
uses forms.

### No LLM Onboarding

The LLM is useful later for extraction into structured facts with human approval. v0.2 proves the
structured fact model first.

### No Manual Repair

Manual repair requires pinning, minimal-change re-solve, and explanation. That belongs after the app
can reliably generate and review baseline schedules.

### No Soft Preferences

v0.2 supports hard unavailability. Soft preferences require explicit solver fields, weights, and
scorecard reporting. They should not be smuggled in as notes.

### No Backward Compatibility

There is no released product schema. v0.2 should shape the correct product model now instead of
supporting old raw scenario files as a user workflow.

## Composition With Future Systems

### Future LLM Intake

Future flow:

```text
document/email/note
  -> LLM extraction draft
  -> cited structured facts
  -> human accept/reject
  -> planning model
  -> compiler
  -> engine
```

Rules:

- LLM output is a draft.
- Accepted facts enter typed planning tables.
- LLM cannot write assignments.
- LLM cannot bypass compile validation.
- LLM citations should point to the source text used for each proposed fact.

### Future Spreadsheet Import

Future spreadsheet import maps into planning tables, not directly into engine scenarios.

### Future Calendar Availability

Future calendar read adapters map free/busy data into provider unavailability drafts. They do not
become assignment sources.

### Future QGenda Integration

Future QGenda read adapters may bootstrap:

- provider roster
- historical opening ledger
- comparison schedules

They must not bypass the planning compiler or the engine validator.

### Future Cloud Deployment

Cloud deployment requires a separate security and tenancy spec. The local MVP should not quietly grow
public hosting assumptions.

## Key Decisions

1. Human source of truth is planning state, not scenario JSON.
2. Scenario JSON is a compiled engine artifact.
3. The compiler is pure and lives in core.
4. SQLite stores planning state and immutable run snapshots.
5. Hono is only an HTTP adapter.
6. React is only a UI adapter.
7. The engine remains the only assignment authority.
8. Exports consume stored schedule runs.
9. No input importers in v0.2.
10. No LLM in v0.2.
11. No backward compatibility with v0.1 scenario files as product input.
