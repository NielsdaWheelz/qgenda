# v0.1 Physician Schedule Generator Spec

Date: 2026-06-17
Status: Implemented and under validation
Mode: Greenfield hard cutover

## Source Context

This spec follows the research pass in `docs/qgenda-physician-scheduling-research.md`.

The user problem is a small hospital physician-group scheduler where QGenda-like tools are perceived to fail at:

- Equal division of burden.
- Avoiding clusters.
- Handling call, weekends, holidays, post-call rest, part-time doctors, and non-call doctors.
- Handling eye/dental clinic eligibility and credit.
- Explaining whether a generated schedule is actually fair.

v0.1 folds the fairness-auditor idea into the generator: every generated schedule must include a hard-rule validation report and a fairness/cluster scorecard. Interactive explanation and repair are v0.2.

## Codebase Survey

Current repo state:

- Existing local product docs:
  - `docs/qgenda-physician-scheduling-research.md`
  - `docs/specs/v0.1-generator-spec.md`
- Existing shared engineering rules: vendored in `docs/rules/`.

Implication:

- v0.1 began as greenfield and now has no legacy schema, UI, API, solver, parser, import pipeline, or compatibility surface to preserve.
- The implementation must not create parallel rule systems. Calendar classification, eligibility, rule IDs, burden weights, validation, scoring, and solver variables must each have one owner module.

## Product Thesis

v0.1 is not a calendar editor. It is a deterministic schedule generator with a visible fairness ledger.

Given a complete scenario file, the system generates a monthly schedule that:

1. Covers required daily list/room/clinic slots.
2. Obeys non-negotiable local rules.
3. Minimizes unfairness and clusters according to explicit weights.
4. Emits a scorecard that lets a human judge whether the result is acceptable.

The generator must not silently guess missing policy. If the scenario is incomplete or contradictory, it must fail with structured validation errors.

## Final State

v0.1 is complete when a developer can run one command against a local scenario file and receive:

- A deterministic generated schedule.
- Solver status and objective score.
- Zero hard-rule violations for feasible scenarios.
- A scorecard showing per-provider call/weekend/holiday/list-position/special-clinic burden.
- Cluster metrics.
- A machine-readable JSON result.
- A simple human-readable table output.
- Tests proving the key rules and scorecard metrics.

Target command:

```bash
qgenda-solve examples/scenarios/month-basic.json --out .tmp/month-basic.result.json
```

Optional local API in the same release:

```http
POST /api/v0_1/schedules/generate
```

The core capability must be implemented as a pure engine API first. CLI and HTTP are thin adapters.

## Hard Cutover Position

There is no legacy code, no fallback solver, no backward compatibility layer, and no alternate "manual fill" path in v0.1.

Rules:

- One canonical scenario schema.
- One canonical schedule result schema.
- One solver path: TypeScript host through the MiniZinc solver adapter.
- No greedy fallback if MiniZinc fails.
- No partial schedule returned as success.
- No hidden default policy for missing business rules.
- No old/alternate model names preserved for convenience.
- No duplicate date/weekend/holiday classification logic.
- No duplicate eligibility logic.
- No duplicate fairness calculations in UI/API adapters.

If generation cannot produce a valid result, return `status: "infeasible"` or `status: "invalid_input"` with diagnostics.

## Target User

- One technical owner building the prototype.

The system is not yet for general physician self-service.

## Capability Contract

### The Engine Can

- Validate a complete scenario.
- Generate a schedule for a fixed planning horizon.
- Assign providers to required slots.
- Enforce hard rules.
- Optimize soft objectives.
- Emit a structured scorecard.
- Emit deterministic output for the same input and solver settings.

### The Engine Cannot

- Infer missing clinic days.
- Infer missing FTE.
- Infer eligibility from provider names.
- Infer policy from prose.
- Import QGenda, calendars, or spreadsheets.
- Explain every individual assignment in natural language.
- Repair a manually edited schedule.
- Guarantee a human will agree with weights that were configured poorly.
- Guarantee optimality unless solver status is `optimal`.

### Status Semantics

- `optimal`: solver proved optimal within configured limits.
- `feasible`: solver found a hard-rule-valid schedule but did not prove optimal. This is allowed only when `allow_feasible_result` is explicitly true.
- `infeasible`: input was valid, but no schedule satisfies the hard constraints.
- `invalid_input`: schema, completeness, or pre-solve validation failed.
- `solver_error`: solver failed unexpectedly; no schedule is returned.

Default v0.1 fixtures should solve to `optimal`.

## Architecture

### Layers

1. `domain`
   - Typed scenario/result models.
   - Date/calendar classification.
   - Provider and slot identity.

2. `rules`
   - Canonical rule catalog.
   - Hard rule IDs.
   - Soft objective IDs.
   - Burden weight IDs.

3. `validation`
   - Pre-solve schema and business validation.
   - Post-solve hard-rule validation.

4. `solver`
   - MiniZinc model construction/invocation.
   - Variable ownership.
   - Objective construction.
   - Solve execution.

5. `scorecard`
   - Fairness ledger.
   - Cluster metrics.
   - Human-readable summary values.

6. `api`
   - Pure function API.
   - Optional HTTP adapter.

7. `cli`
   - Local command wrapper.
   - Reads scenario JSON.
   - Writes result JSON/table.

### Dependency Direction

Allowed:

- `cli -> api -> validation -> solver -> domain/rules`
- `api -> scorecard -> domain/rules`
- `validation -> domain/rules`

Forbidden:

- `domain` importing solver code.
- `rules` importing API/CLI code.
- `scorecard` using solver internals directly.
- CLI/HTTP recomputing business rules.
- UI or API creating hidden assignments outside the engine.

## Technology Decisions

### Language

Use TypeScript for v0.1.

Reasons:

- TypeScript can own the domain model, scenario/result schemas, CLI, future API, and future UI in one typed system.
- Effect gives typed error, service, resource, and process composition for the failure-heavy scheduler workflow.
- Bun keeps the toolchain small by owning package management, scripts, test execution, and local runtime.
- MiniZinc can own the constraint model as a target language behind a TypeScript-owned solver port.

### Solver

Use MiniZinc through a TypeScript `Solver` port.

Preferred backend:

- OR-Tools through MiniZinc when installed and configured.

Reasons:

- The problem is discrete assignment with Boolean variables.
- Rules are mostly cardinality, sequence, eligibility, and integer fairness constraints.
- v0.1 group sizes should be small enough for exact or near-exact solves.
- Direct OR-Tools does not provide an official TypeScript API; MiniZinc provides a solver-model boundary that TypeScript can invoke.
- The scenario/result contracts remain solver-agnostic, so a future direct OR-Tools adapter can replace MiniZinc without changing product APIs.

### Schema

Use Effect Schema.

Rules:

- Reject unknown top-level fields unless explicitly marked extension fields.
- Keep schema version in every request.
- Keep all provider and slot references ID-based, not name-based.

### Persistence

No database in v0.1.

The scenario JSON is the source of truth. The result JSON is generated output.

## Domain Model

### Provider

Required fields:

```json
{
  "id": "dr_smith",
  "display_name": "Dr. Smith",
  "fte": 1.0,
  "call_eligible": true,
  "eye_eligible": false,
  "dental_eligible": true,
  "active_from": "2026-01-01",
  "active_until": null,
  "unavailable_dates": ["2026-01-12"]
}
```

Rules:

- `id` is stable and unique.
- `display_name` is not used for joins.
- `fte` must be greater than 0 and less than or equal to 1.0 for v0.1.
- Part-time doctors can be modeled as `fte < 1.0`.
- If a provider is not `call_eligible`, they cannot be first, second, last, call, weekend call, or holiday call.
- Eye and dental eligibility are independent of call eligibility.

### Day Demand

Each date has explicit demand.

```json
{
  "date": "2026-01-05",
  "room_count": 6,
  "normal_list_slots": 5,
  "eye_slots": 0,
  "dental_slots": 1,
  "call_required": true,
  "holiday_id": null,
  "weekend_block_id": null,
  "notes": "optional non-clinical note"
}
```

Rules:

- `normal_list_slots` is the number of ordinary list positions to assign.
- `room_count` is capacity validation, not assignment count.
- `normal_list_slots + eye_slots + dental_slots <= room_count`.
- v0.1 does not infer demand from weekdays.
- If a day is omitted from the horizon, input is invalid.

### Generated Slot Types

The engine expands each day into slots:

- `normal_first`
- `normal_second`
- `normal_middle`
- `normal_last`
- `eye_middle`
- `dental_middle`

Expansion rules:

- If `normal_list_slots == 1`, the only ordinary slot is `normal_first_last`.
- If `normal_list_slots == 2`, slots are first and last.
- If `normal_list_slots == 3`, slots are first, second, last.
- If `normal_list_slots >= 4`, slots are first, second, one or more middle, last.
- Eye/dental slots are middle-equivalent slots and also count toward eye/dental burden.

Open decision for domain expert:

- If there are only one or two normal slots, should non-call providers be completely excluded from that day because all slots are first/last? v0.1 default: yes.

### Holiday

```json
{
  "id": "memorial_day",
  "date": "2026-05-25",
  "label": "Memorial Day",
  "class": "major",
  "weekend_block_id": "memorial_day_weekend"
}
```

Rules:

- Holiday dates are explicit.
- Holiday class is one of `major`, `minor`.
- Holiday class controls burden weight only.

### Weekend Block

```json
{
  "id": "memorial_day_weekend",
  "dates": ["2026-05-22", "2026-05-23", "2026-05-24", "2026-05-25"],
  "split_required": true,
  "required_distinct_call_providers": 2
}
```

Rules:

- Friday night belongs to the weekend block.
- If `split_required`, the block's call assignments must use exactly `required_distinct_call_providers` providers.
- v0.1 does not optimize nuanced half-day split patterns; it enforces distinct provider count and no consecutive calls.

### Opening Ledger

Optional but recommended:

```json
{
  "provider_id": "dr_smith",
  "call_burden": 3.0,
  "weekend_burden": 1.0,
  "holiday_burden": 0.0,
  "first_count": 4,
  "second_count": 3,
  "middle_count": 8,
  "last_count": 2,
  "eye_count": 1,
  "dental_count": 0
}
```

Rules:

- If omitted, all opening ledger values are zero.
- This is not a historical import feature. It is a native v0.1 input field.
- Opening ledger lets a partial-year schedule remain annual-fair.

## Core API Design

### TypeScript API

```ts
import { generateSchedule } from "./src/api/generateSchedule"

const result = await generateSchedule(request)
```

Contract:

- Accepts a `ScheduleRequest` model or JSON-compatible dict.
- Returns a `ScheduleResult` model.
- Does not read scenario/result files.
- Does not write scenario/result files.
- Does not call network services.
- Does not mutate product global state.

The MiniZinc adapter may use temporary solver data files behind the `Solver` port. That file IO is solver process plumbing, not CLI-owned scenario/result import/export.

### CLI

```bash
qgenda-solve SCENARIO_JSON --out RESULT_JSON
```

Options:

- `--table`: also print human-readable table to stdout.
- `--strict`: fail nonzero unless status is `optimal`.
- `--pretty`: pretty-print JSON.

Default:

- Nonzero exit for `invalid_input`, `infeasible`, `solver_error`.
- Zero exit for `optimal`.
- Zero exit for `feasible` only if request explicitly allowed feasible results.

### HTTP API

Only if implemented after core engine and CLI:

```http
POST /api/v0_1/schedules/generate
Content-Type: application/json
```

Response:

- `200` for `optimal` or explicitly allowed `feasible`.
- `400` for `invalid_input`.
- `409` for `infeasible`.
- `500` for `solver_error`.

No auth in v0.1.

No persistence in v0.1.

## Rule Catalog

Every rule has:

- Stable ID.
- Severity: `hard` or `soft`.
- Owner module.
- Description.
- Metric emitted in result.

### Hard Rules

#### `H_COVER_ALL_SLOTS`

Every generated slot must be assigned exactly one provider.

#### `H_PROVIDER_ONE_SLOT_PER_DAY`

A provider can receive at most one slot per date.

#### `H_PROVIDER_ACTIVE`

Provider must be active on the assignment date.

#### `H_PROVIDER_AVAILABLE`

Provider cannot be assigned on an unavailable date.

#### `H_ROOM_CAPACITY`

Day's total generated slots cannot exceed `room_count`.

#### `H_CALL_ELIGIBLE_FOR_FIRST`

Any first-equivalent slot must be assigned to a call-eligible provider.

First-equivalent slots:

- `normal_first`
- `normal_first_last`

#### `H_CALL_ELIGIBLE_FOR_SECOND_LAST`

Second and last slots must be assigned to call-eligible providers.

Rationale: user note says non-call doctors are never first, never second, never last.

#### `H_NON_CALL_NO_WEEKEND_OR_HOLIDAY`

Weekend and holiday assignments must be assigned to call-eligible providers.

#### `H_NO_CONSECUTIVE_CALLS`

For each provider, `call[p, d] + call[p, d+1] <= 1`.

#### `H_POST_CALL_DAY_OFF`

If provider has call on date `d`, provider cannot be assigned any slot on date `d+1`.

#### `H_EYE_ELIGIBILITY`

Eye slots require `eye_eligible`.

#### `H_DENTAL_ELIGIBILITY`

Dental slots require `dental_eligible`.

#### `H_WEEKEND_BLOCK_SPLIT`

If a weekend block has `split_required`, call assignments in that block must use exactly `required_distinct_call_providers`.

#### `H_HORIZON_COMPLETE`

Every date from start to end must have a `DayDemand` entry.

#### `H_CALL_REQUIRES_FIRST_SLOT`

Every call-required day must have a first-equivalent ordinary slot so call can be derived from list order.

### Soft Rules

#### `S_BALANCE_CALL_BURDEN`

Minimize FTE-normalized deviation from target call burden among call-eligible providers.

#### `S_BALANCE_WEEKEND_BURDEN`

Minimize FTE-normalized deviation from target weekend burden among call-eligible providers.

#### `S_BALANCE_HOLIDAY_BURDEN`

Minimize FTE-normalized deviation from target holiday burden among call-eligible providers.

#### `S_BALANCE_FIRST_COUNT`

Minimize first-position count spread among call-eligible providers.

#### `S_BALANCE_SECOND_COUNT`

Minimize second-position count spread among call-eligible providers.

#### `S_BALANCE_MIDDLE_COUNT`

Minimize middle-position count spread among all eligible working providers, FTE-normalized.

#### `S_BALANCE_LAST_COUNT`

Minimize last-position count spread among call-eligible providers.

#### `S_BALANCE_EYE_COUNT`

Minimize eye count spread among eye-eligible providers.

#### `S_BALANCE_DENTAL_COUNT`

Minimize dental count spread among dental-eligible providers.

#### `S_BALANCE_WORKDAY_COUNT`

Minimize FTE-normalized workday-count spread across providers.

#### `S_AVOID_WORK_CLUSTERS`

Minimize long runs of consecutive assigned workdays.

#### `S_AVOID_WEEKEND_CLUSTERS`

Minimize repeated weekend-block assignments for the same provider when possible.

## Call Derivation

v0.1 does not model a separate call slot.

Call is derived:

- If `day.call_required == true`, the provider assigned to the first-equivalent slot has call.
- If no first-equivalent slot exists on a call-required day, input is invalid.
- If Friday date is in a weekend block, the Friday first-equivalent call is weekend call.
- Holiday call is call on any date with `holiday_id`.

Rationale:

- This matches the user note: "the person who's first always does call."
- It keeps v0.1 smaller and prevents disagreement between list order and call assignment.

## Weekend Classification

Central owner: `src/domain/calendar.ts`.

Weekend is true when:

- Date is Saturday.
- Date is Sunday.
- Date appears in a `WeekendBlock`.
- Date is Friday and the day has Friday-night/weekend call semantics through a weekend block.

The system must not duplicate weekend logic in solver, scorecard, and CLI.

## Fairness Ledger

For each provider, emit:

```json
{
  "provider_id": "dr_smith",
  "fte": 1.0,
  "workday_count": 12,
  "call_count": 3,
  "call_burden": 3.5,
  "weekend_count": 1,
  "weekend_burden": 1.5,
  "holiday_count": 0,
  "holiday_burden": 0.0,
  "first_count": 3,
  "second_count": 2,
  "middle_count": 6,
  "last_count": 1,
  "eye_count": 0,
  "dental_count": 1,
  "target_call_burden": 3.2,
  "call_delta": 0.3
}
```

Aggregate scorecard emits:

- Max/min spread per ledger.
- Variance per ledger.
- Largest positive/negative delta.
- Providers excluded from each pool.
- Hard violations count.
- Objective contribution by soft rule.
- Workday-count aggregate.

## Burden Weights

Default weights are explicit input defaults owned by `src/rules/weights.ts`.

Initial defaults:

```json
{
  "weekday_call": 1.0,
  "friday_night_call": 1.25,
  "weekend_call": 1.5,
  "minor_holiday_call": 1.5,
  "major_holiday_call": 2.0,
  "first_position": 1.0,
  "second_position": 1.0,
  "middle_position": 1.0,
  "last_position": 1.0,
  "eye_slot": 1.0,
  "dental_slot": 1.0
}
```

These are not sacred. v0.1 must make them visible and editable in the scenario.

## Cluster Metrics

Emit:

- Consecutive call violations: must be zero.
- Post-call assignment violations: must be zero.
- Max consecutive workdays by provider.
- Workday run distribution by provider.
- Weekend blocks assigned by provider.
- Consecutive weekend blocks by provider.
- Call spacing minimum and average by provider.

For v0.1, cluster metrics are mostly reporting plus soft penalties. Only consecutive call and post-call day off are hard.

## Validation

### Preflight Validation

Must reject:

- Unknown schema version.
- Duplicate provider IDs.
- Missing horizon dates.
- Day demand outside horizon.
- Holiday outside horizon.
- Weekend block date outside horizon.
- Slot demand greater than room count.
- Call-required day with no ordinary first-equivalent slot.
- Eye slot when no active eye-eligible provider could possibly cover it.
- Dental slot when no active dental-eligible provider could possibly cover it.
- Weekend/holiday/call demand when no active call-eligible provider could possibly cover it.
- `required_distinct_call_providers` greater than available call-eligible providers.
- Invalid FTE.
- Unknown provider references in opening ledger.

### Postsolve Validation

Must independently check:

- All hard rules.
- Assignment references are valid.
- Every slot assigned exactly once.
- No provider assigned twice in a day.
- Derived call semantics.
- Scorecard count consistency.

Postsolve validation cannot use MiniZinc variable values directly. It checks the generated assignment list.

## Solver Modeling

Variables:

- `x[p,d,s]`: provider `p` assigned to slot `s` on date `d`.
- `works[p,d]`: provider has any assignment on date `d`.
- `call[p,d]`: provider has derived call on date `d`.
- `weekend_assignment[p,b]`: provider has assignment in weekend block `b`.
- Ledger counters as integer expressions.
- Deviation variables for fairness objectives.

Hard constraints:

- Generated from rule catalog.
- Each hard rule has a test.

Objective:

- Hierarchical weighted objective encoded in MiniZinc with explicit objective components:
  1. Hard constraints are constraints, not penalties.
  2. Minimize rest/fatigue/cluster penalties.
  3. Minimize call/weekend/holiday unfairness.
  4. Minimize list-position and special-clinic unfairness.
  5. Minimize general workday imbalance.

No hard constraint may be converted into a soft penalty in v0.1.

## Acceptance Criteria

### Functional

- Given `month-basic.json`, CLI returns `status: "optimal"`.
- Every required slot is assigned.
- Hard-rule report has `violation_count: 0`.
- Non-call providers are never first, second, last, call, weekend, or holiday call.
- Eye slots only use eye-eligible providers.
- Dental slots only use dental-eligible providers.
- No provider has consecutive calls.
- No provider works the day after call.
- Long weekend fixture uses exactly two distinct call providers when configured.
- Result contains fairness scorecard.
- Result contains cluster metrics.
- Same input and seed produce byte-stable assignment ordering and equivalent result values.

### Infeasibility

- Given a fixture with one call-eligible provider and consecutive call-required days, result is `infeasible`, not partial success.
- Given a fixture with an eye slot but no eye-eligible providers, result is `invalid_input`.
- Given a fixture where demand exceeds room capacity, result is `invalid_input`.

### Engineering

- All schema models are typed.
- CLI does not contain scheduling rules.
- HTTP adapter, if present, does not contain scheduling rules.
- Rule IDs appear in validation errors and scorecard objective contributions.
- Tests cover all hard rules.
- Test suite runs locally with one command.

## Non-Goals And Rationale

### No Auth

Single-user local prototype. Adding auth now does not reduce the hardest risk, which is domain correctness.

### No Security Program

Use synthetic or non-PHI provider-only data. Do not enter patient data. If real patient/care-context data enters scope, v0.1 is not the right posture.

### No Import/Export

Native JSON is the v0.1 scenario API. Spreadsheet/calendar/QGenda imports would obscure whether the solver model is correct.

### No Explain/Repair

v0.1 scorecard tells whether a schedule is good. v0.2 can answer why a particular assignment happened and repair pinned changes.

### No Backward Compatibility

There is no released schema. Schema can be shaped correctly now.

## Composition With Future Systems

The core engine composes by accepting and returning canonical JSON.

Future adapters:

- QGenda read adapter -> `ScheduleRequest.opening_ledger` or historical comparison data.
- Spreadsheet adapter -> `ScheduleRequest`.
- Calendar free/busy adapter -> provider unavailable dates.
- EHR/OR/clinic template adapter -> `DayDemand`.
- UI editor -> `ScheduleRequest`.
- Exporters -> consume `ScheduleResult`.

Rules:

- Adapters cannot bypass preflight validation.
- Adapters cannot emit assignments directly.
- Adapters cannot own business rules.
- Future integrations must map into the canonical scenario schema.

This keeps the solver independent from QGenda, EHRs, calendars, and UI choices.

## Open Domain Questions

These should be answered before hard-coding defaults beyond v0.1 fixtures:

1. If there is only one normal list slot, is that slot both first and last, and therefore call-eligible only?
2. If there are exactly two normal list slots, is the second slot also last, and therefore call-eligible only?
3. Does post-call day off apply after every first-position call, including Friday night/weekend call?
4. Can eye/dental be assigned on a post-call day?
5. Can non-call doctors work weekend middle slots if there is no call, or are all weekend assignments call-eligible only?
6. Are part-time doctors always non-call, or is that just true for the current group?
7. Are holiday and weekend burdens separate ledgers or should holiday weekend count in both?
8. Is second position truly forbidden for non-call doctors, or is it forbidden because second tends to be backup call?
9. Are "rooms" and "lists" always identical in burden?
10. Should preference requests exist in v0.1 fixtures, or wait for v0.2?
